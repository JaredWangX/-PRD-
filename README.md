# -PRD-
请友友们参考，可以在基础上进行修改。

> 模板用途：**帮助产品、设计、研发和测试对齐问题、目标、交付范围与验收标准。复制一份后即可用于新需求。
>
> **填写约定：**把 `{{……}}` 替换成项目内容；“填写说明”和“示例”可在填写完成后删除。文中示例均为虚构，不代表真实业务数据，也不是建议直接采用的指标或阈值。

## 使用方法

1. 先确定本次要交付什么。一份 PRD 尽量覆盖一个边界清楚的功能或版本；大型项目可以保留总览，再拆成若干子需求。
2. 先写问题，再讨论方案。优先完成背景、用户、目标与范围，尽早邀请设计、研发和测试共同补充，不必等整份文档写完。
3. 按需求复杂度展开。小改动可合并章节，沿用已有规范的内容直接给出链接。涉及资金、数据变更、多个角色或外部依赖时，应展开对应规则和异常情况。
4. 记录已知事实，也记录不确定性。没有数据就填写“暂无，计划如何获取”；未确认的规则写入“待解决问题”，注明负责人和截止时间。
5. 把文档保持为当前共识。讨论中改变了范围、规则或验收标准，应及时更新本文与关联工单，避免各处出现不同版本。

### 哪些内容必须回答

| 必须回答的问题 | 对应章节 | 怎么判断写够了 |
| --- | --- | --- |
| 为什么值得做？ | 2. 背景、问题与价值 | 能说清谁遇到了什么问题，依据是什么，为什么现在处理 |
| 为谁做？ | 4. 用户与场景 | 能识别本次目标用户及其具体任务 |
| 怎样算有效？ | 3. 目标与成功指标 | 有明确指标、统计口径、目标及观察时间 |
| 本次做哪些、不做哪些？ | 5. 方案与范围 | 交付边界明确，可以据此排期和取舍 |
| 用户会经历什么？ | 6—8. 流程、功能与非功能需求 | 主流程、关键异常、业务规则和必要约束清楚 |
| 怎样判断做对了、可以发布？ | 10—12. 验收、依赖与发布 | 可验证，有负责人，发布条件明确 |

> 职责说明：产品牵头明确用户问题、业务规则、预期行为和成功标准；设计与研发共同完善方案；研发负责技术实现方案；测试共同补充验证方法。涉及实现取舍时，记录约束、结论和技术方案链接即可，不必把架构设计全部写进 PRD。
